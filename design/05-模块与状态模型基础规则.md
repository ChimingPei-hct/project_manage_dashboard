# 模块与状态模型基础规则

## 1. 模块目标

定义看板的核心数据抽象:**模块(Module)** 与 **状态(Status)** 的对应关系、颜色语义、三层分离原则。所有 Schema 文档(06–09)都建立在本约束之上。

## 2. 边界与职责

### 管什么

- module 的统一概念模型(`scope=pdt` vs `scope=ltc`)
- 状态的颜色语义(绿/黄/红)与可选字段(KPI、风险说明)
- 配置 / 当前态 / 历史 / 快照四类数据的关系与不变量

### 不管什么

- 字段的具体类型与命名 → `06`–`09`
- 谁能改 → `10`
- 怎么展示 → `13`

## 3. 模块统一模型

无论 PDT 级总览卡片还是 LTC 级子模块,都使用**同一份 `modules.json`**,通过 `scope` 字段区分。统一模型的好处:

- 后端权限/校验逻辑只需一套
- 前端"模块卡片 + StatusCell"组件可复用
- 未来扩展第三种 scope(如跨 LTC 横切模块)无需迁移现有数据

### 3.1 字段(完整定义见 `06`)

| 字段 | 含义 |
|------|------|
| `id` | 全局唯一标识 |
| `scope` | `"pdt"` 或 `"ltc"` |
| `ltc_id` | `scope=ltc` 时必填,引用 `ltcs[].id`;`scope=pdt` 时必须为 `null` |
| `group` | 分组名(如"研发-感知包"、"硬件和底软"),前端按 group 渲染分组 |
| `name` | 模块名 |
| `order` | 排序 |
| `owner_open_id` | 负责人飞书 open_id |
| `kpi_fields` | KPI 字段定义(PDT 级常用,LTC 级一般为空) |
| `sub_items` | 子项列表(LTC 级常用,如"MCU 底软"下面的色块) |
| `metadata` | 预留扩展 |

## 4. 状态模型

### 4.1 颜色语义(全局唯一定义)

| 颜色 | 含义 | 触发条件示例 |
|------|------|------|
| **绿(green)** | 进展正常 | 按计划推进、无阻塞 |
| **黄(yellow)** | 进展有风险 | 可能延期、依赖项不稳、需关注但未阻塞 |
| **红(red)** | Delay 或 Block | 已确认延期 / 已被阻塞 / 关键事故 |

- 颜色不允许有第四种语义
- 颜色编码常量(色值)定义在 `12-前端实现约束.md`,后端只存枚举字符串

### 4.2 状态的两个层级

每个模块的状态包含:

- **模块整体色**(`module_color`):该模块在父视图(PDT 卡片/LTC 列)的灯
- **子项色**(`sub_items_color`):仅当 `modules[*].sub_items` 非空时使用,逐子项独立色块

**不变量**:`module_color` 不强制等于子项中最差色,允许 Owner 主观判断给出整体灯。但 UI 应在两者不一致时给提示(子项有红但整体绿 → 黄色三角警告)。

### 4.3 风险说明(`risk_note`)

- `module_color in {yellow, red}` 或任一 `sub_items_color != green` 时,`risk_note` **必填且非空**(后端校验)
- `module_color == green` 且无任何非绿子项时,`risk_note` 可空
- 文案长度 1–500 字符

### 4.4 KPI(`kpi_values`)

- PDT 级卡片常用(如"自动驾驶里程""问题闭环率")
- 每个 KPI 是字符串(显示原文),允许 `"38%(目标 50%)"`、`"5.16 TR5-1"` 这类带格式文本
- 后端不解析 KPI 语义,只透传

## 5. 数据分层与不变量

| 层 | 文件 | 写规则 | 读规则 |
|---|------|--------|--------|
| 配置层 | `modules.json` / `ltcs.json` / `pdt.json` | 仅管理员可改;改变结构 | 前端首屏拉,缓存到 SSE 触发 |
| 当前态层 | `module_status.json` | Owner 改自己模块;**完整覆写** | 前端首屏拉,SSE 触发重拉 |
| 历史层 | `module_updates.jsonl` | **append-only**,任何当前态变更必追加一行 | 详情页按需拉 |
| 快照层 | `weekly_snapshots/snapshot-YYYY-Www.json` | 冻结时一次性写,**写后只读** | 历史周切换时拉 |

### 5.1 不变量

- **删除模块时**:`module_status` 中对应 entry 同步删除;`module_updates.jsonl` **不动**(历史不可篡改);已有 snapshot 保留(冻结只读)
- **当前态与历史流**:每次 `PUT /api/status/{id}` 必须:1) 覆写 `module_status.json` 中 `id` 的 entry;2) 追加一行 `module_updates.jsonl` 记录 before/after
- **当前态与快照**:周快照是某时刻 `module_status.json` 的完整拷贝,与历史流一致

### 5.2 时间戳

- 一律 ISO 8601 with timezone(`+08:00`),如 `2026-05-22T15:30:00+08:00`
- 所有写操作刷新对应 entry 的 `updated_at`

## 6. 执行约束

- 新增模块字段时,先改 `06`,再改后端,最后改前端
- 新增状态字段时,先改 `07`/`08`,再改后端,最后改前端
- 颜色枚举严禁扩充到第四种;如确需"灰色 = 未启动",视为新功能,要先改本约束
- 风险说明的必填规则在后端实现一次,前端再做一次提示(双层防护)

## 7. 禁止项

- **禁止把 `module_color` 写成色值**(只能存 `"green"`/`"yellow"`/`"red"`)
- **禁止改写历史流**(任何 jsonl 行改动 = 篡改)
- **禁止把当前态字段与配置字段混在同一文件**(如把 owner 写进 status)
- **禁止跳过历史流直接改当前态**(双写不可分割,任何一处失败必须回滚)

## 8. 扩展方式

- 增加颜色语义(如"灰色未启动"):升级本文件 → 升级 `07`/`08`/`12`,并提供数据迁移
- 增加子项二级结构(子项的子项):新增 `sub_items[*].sub_items`,前端递归渲染;v1 不做
- 多 Owner 协作(一个模块多负责人):`owner_open_id` 改为 `owner_open_ids: []`,权限判定改"任一命中放行"
